## 一 · 先修这三条:它们现在正在骗人

### 1. 一个不可逆删除接口,唯一的防穿越控制没有任何测试

`codexinfo.delete_transcripts` 有六道闸。把 `resolve()` 之后 `relative_to(root)`
那一道**整个删掉,32 条用例一条不红**。

不是"忘了写用例",而是所有现成用例的输入都被多道闸同时拦住,
逐个投毒量过:六道闸里任何一道单独删掉,每一条现成输入仍然被拦。
一个每道闸都可以被单独删掉而不报警的套件,挡不住纵深被一层层磨掉。

真正只有归属闸能拦的输入是 **Windows 目录联接**:路径里没有 `..`、没有反斜杠、
没有冒号,不是绝对路径,首段合法,后缀合法,`is_file()` 为真,
而且 `is_symlink()` **为假**(联接在 Python 眼里不是符号链接),
但 `resolve()` 落在树外。这不是假想形状, 这套东西本来就用联接部署目录。

**已修**(本次会话):补了这条用例,投毒确认能红;另补上限闸与未配置分支两条。
其余两道闸(绝对路径、`..` 段)仍然没有独当一面的用例,已在用例 docstring 里写明,
免得下一个人把绿色读成"六道闸都有覆盖"。

`clean.tempgit` 删目录;`delete_transcripts` 删文件,而且不走动作表;
`repo.commitpush` 会把东西推出这台机器。

`scripts/task_console/README.md:97` 另有一句"任何地方都没有 push 按钮",同样已经不成立。
`repos.py` 文件头第 17 行说"网络动作只有 fetch",而同文件 784 行在 `git push`。

一个以"不让坏掉的东西看起来正常"为存在理由的工具,
它的文档正在向读者保证一件它做不到的事,而且保证的恰好是安全边界。
**这是这份方案里唯一一条"不修就是错的"。**

## 五 · 文档:两份变三份,**不是**六份

现状 244 行,而项目有 9598 行源码、约 20 个模块、18 条 HTTP 路由、一张动作表、
一个数据库 schema。新来的人(或半年后的自己)答不上来的问题:
数据是怎么进来的、有哪些端点、动作表怎么加一项、ingester 谁在调、不调会怎样。

方案刻意**只增一份**:

1. **根 `README.md`** 压到约 40 行。这是什么、不变量("没查 ≠ 没问题")、装什么、跑什么、许可。
   具体清单一律不放,只放指针。现在 12-21 行那两段实现细节搬走。
2. **`scripts/task_console/README.md`** 收到约 140 行,只回答"怎么在一台机器上配起来并用起来"。
   环境变量表**补三行**(有三个真实生效的变量不在表里,而对账测试按设计看不见它们,
   它只扫 `scripts/task_console/*.py`,那三个派生自 `guards/tools/datadir.py`)。
   加一小节《先把 ingester 跑起来》:首次 backfill 命令、必须每小时调一次、
   因为事件日志是约五天的环形缓冲。不贴计划任务 XML,那属于机器侧。
3. **新增 `scripts/task_console/INTERFACE.md`** 约 80 行,两张表:18 条路由、19 个模块。
   这是唯一新增的一份,理由是它覆盖的两个问题现在**完全无人回答**,
   而且这两张表最容易机器对账。

**不新建** `ARCHITECTURE.md` / `CONTRIBUTING.md` / `CHANGELOG.md`:
它们没有可对账的内容,落地就是三份会漂的散文。

### ⚠ 上面这条闸门策略已经作废(2026-09-15 改)

原文写的是"三张清单表各配一条双向对账测试"。那是错的,而且错得很典型:
**这份方案自己犯了它反对的毛病**, 给每一份重复配一个对账闸,
而不是消灭重复本身。一个对账闸的存在,本身就是承认这里有两份。

仓里当时已经有三个对账闸,而它们的 docstring 说的是同一句话的三种说法。
再加四个同款之后,维护的就不是代码,是七个提醒你"这里有两份"的测试。

新的顺序是:

1. **能不能删掉第二份**(让它派生出来)-> 零闸门
2. 必须存在但**能生成** -> 零闸门
3. 两份都得手写、而且其中一份在这个仓之外 -> **才**上闸门

照这条重算的结果(均已落地):

| | 原方案 | 实际做法 |
|---|---|---|
| 调色板(颜色三份手写) | 保留对账闸 | 三元组成为唯一来源,另两份用纯 CSS 派生。**删掉 89 行测试** |
| ok_codes(三份手写) | 保留对账闸 | server 只留一处解析并借用 freshness 的规则。那条对账用例原本是假的,已改成真的调 server |
| 环境变量表 | 保留 | **保留**, 第二份是仓外的启动器,消灭不掉,这是唯一真正需要闸门的一处 |
| README 能力清单 | 新增对账闸 | **不加**。三处枚举直接删掉,指向动作表那个唯一权威 |
| 路由表 / 模块表 | 新增两张表 + 两个闸 | **不加表** |
| 死 CSS | 新增测试文件 | **并进** `test_page_js.py`(它已有 CSS 解析器和负对照) |

净效果:对账闸 3 -> 1,新增测试文件 0。

原则改成一句话:**凡是能变成一份的就变成一份,变不成再上闸门。**
"能对账的就上闸门"是次优解, 它把重复合法化了。

另:`server.py` 顶部 41 行 docstring 是 README 的第二份副本,而且**已经漂了两处**。
砍到 6-8 行,只留"这是什么 + 指针",加上那条确实属于代码旁边的不变量
(任务名经环境变量进 PowerShell,绝不拼进命令串, 它就在 `act.ps1` 隔壁)。

## 六 · `console.html` 3656 行要不要拆

复核推翻了原始的拆分方案(它对"会牵动哪些测试"判断有误,照做会得到红的套件)。
所以这里只给结论,不给步骤:

- 服务端只对 `console.html` 做 `__TOKEN__` 替换,而 `/vendor/` 路由**只认 `.css` 和 `.js`**。
  拆成多文件要么改那条路由的 MIME 表,要么让新文件走 vendor, 两条都不是免费的。
- 单文件有一个真实好处:这台控制台正是出事的时候要打开的,一个文件少一次失败机会。
- 因此:**这一项不排进近期**。真要拆,先拆 CSS(1012 行,依赖最少),
  且必须先有第三节那道死 CSS 闸门, 没有它,拆的过程中丢掉一条规则不会有任何人知道。
